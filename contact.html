문의 안내

오류 제보, 기능 요청, 사용 경험 피드백은 공개된 경로로 보내주시면 확인하기 쉽습니다.

민감한 개인정보, 비밀번호, API 키, 운영 토큰은 문의 내용에 포함하지 않는 것을 권장합니다.

Bug reports, feature requests, and usage feedback are easiest to review when they come through a public, trackable channel.

Do not include sensitive personal data, passwords, API keys, or production tokens in a public report.

Recommended contact routes

GitHub Issue GitHub Repository Tistory

오류 제보에 있으면 좋은 정보

  • 문제가 발생한 페이지 주소와 도구 이름
  • 입력 예시 또는 재현 가능한 최소 샘플
  • 기대한 결과와 실제 결과
  • 브라우저 종류와 버전, 모바일/데스크톱 여부
  • 가능하다면 스크린샷이나 콘솔 오류 메시지

What helps in a bug report

  • The tool page URL and the exact feature involved
  • A minimal reproducible input or sample
  • The expected result versus the actual result
  • Browser name/version and whether it happened on mobile or desktop
  • A screenshot or console error if available

오류 제보·기능 요청

GitHub Issue가 가장 확실합니다. 기록이 남고 진행 상황이 공개되며, 같은 문제를 겪은 사람이 검색으로 찾을 수 있습니다. 계정이 없으면 블로그 댓글로도 됩니다.

개인정보 관련 요청

이 사이트는 계정을 만들지 않고 입력값을 서버로 보내지 않으므로, 삭제를 요청할 개인정보가 애초에 없습니다. 처리 방식에 대한 질문은 개인정보 처리 안내를 먼저 보시고, 남는 의문은 이슈로 남겨주세요.

저작권·삭제 요청

이 사이트의 문서나 코드가 권리를 침해한다고 판단되면 해당 주소와 근거를 이슈로 알려주세요. 확인되면 내리는 것을 우선하고, 판단이 필요한 부분은 그 이슈에서 공개적으로 논의합니다.

광고·제휴 문의

도구 화면을 가리거나 결과를 밀어내는 형태의 광고는 받지 않습니다. 그 외의 제안은 저장소나 블로그 경로로 보내주세요.

Where to send what

This is a one-person project, so there is deliberately only one main channel. Sending things this way makes them hard to lose.

Bugs and feature requests

A GitHub Issue is the most reliable route: it leaves a record, progress is public, and the next person with the same problem can find it. Without an account, a blog comment works too.

Privacy requests

There are no accounts and input is not sent to a server, so there is no personal data to delete. For questions about how processing works, start with the privacy notice and raise an issue for anything it does not answer.

Copyright and takedown

If something here infringes your rights, open an issue with the URL and the basis for the claim. Removal comes first where the claim is clear; anything requiring judgement is discussed openly in that issue.

Advertising and partnerships

Ad formats that cover a tool's working area or push results out of view are not accepted. Other proposals can go through the repository or blog.

답변에 대해 미리 말씀드립니다

얼마나 걸리나요?

본업이 따로 있어서 즉시 답하기는 어렵습니다. 도구가 잘못된 결과를 내거나 모바일에서 화면이 깨지는 문제는 먼저 봅니다. 기능 요청은 확인은 하되 반영을 약속드리지 못합니다.

어떤 요청은 받기 어렵나요?

개별 코드에 대한 기술 지원, 맞춤 도구 개발, 사이트 소스를 이용한 상업 서비스 구축 상담은 다루지 않습니다. 도구 자체의 동작 범위를 벗어나는 일이라 답을 드려도 도움이 되지 않습니다.

보안 문제를 발견했다면

다른 사용자에게 피해가 갈 수 있는 내용이라면 공개 이슈에 재현 방법을 그대로 적기보다, 영향 범위만 먼저 알려주세요. 확인 후 조치하고 나서 내용을 공개하는 편이 안전합니다.

보내지 말아야 할 것

재현용이라도 실제 비밀번호, API 키, 운영 토큰, 고객 데이터는 넣지 마세요. 공개 이슈는 검색에 노출되고 한 번 올라간 값은 되돌리기 어렵습니다. 값의 형태만 남기고 내용은 바꿔서 보내주시면 충분합니다.

What to expect from a reply

How long does it take?

There is a day job, so immediate replies are not realistic. Tools producing wrong results and layouts breaking on mobile are looked at first. Feature requests are read, but implementation is not promised.

What is out of scope?

Technical support for your own code, custom tool development, and consulting on building a commercial service from this source are not covered. They fall outside what the tools do, so an answer would not actually help.

Found a security problem?

If it could affect other users, describe the impact first rather than posting full reproduction steps publicly. Fixing before disclosing is the safer order.

What not to send

Never include real passwords, API keys, production tokens or customer data, even as a reproduction case. Public issues are indexed by search engines and a posted value is hard to take back. Keep the shape of the value and change the contents.

기능 요청은 이렇게 보내주시면 좋습니다

어떤 문제를 줄이고 싶은지

단순히 “도구 추가”보다, 어떤 반복 작업을 줄이고 싶은지 설명해 주시면 우선순위를 정하기 쉽습니다.

입력과 출력 형식

예상 입력 예시와 원하는 결과 형식을 함께 적으면 실제 구현 가능성을 빠르게 판단할 수 있습니다.

브라우저 처리 가능 여부

서버 없이 가능한 작업인지, 외부 API가 필요한 작업인지 알려주면 방향을 잡는 데 도움이 됩니다.

검토 우선순위

많이 쓰는 도구의 오류, 보안상 오해를 부를 수 있는 문구, 모바일에서 깨지는 UI를 우선 확인합니다.

What makes a feature request useful

Describe the workflow pain

“Add a tool” is less actionable than explaining which repetitive task you want to shorten.

Show expected input and output

Concrete examples help determine scope and implementation feasibility much faster.

Note whether browser-only is possible

It helps to know whether the feature can stay client-side or would depend on an external API.

Review priority

Issues in frequently used tools, confusing security copy, and mobile layout problems are reviewed first.
